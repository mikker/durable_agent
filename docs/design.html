one gem · one sidecar · one database

durable_agent: pi-durable as one Rails gem

One bundle add, one migration, one extra process, one database. pi-durable keeps its state in the app's own Postgres or SQLite, whichever database.yml names, the same way Rails picks its adapter.

This page describes the gem: a Rails engine with a bundled Node sidecar, implemented against the contract in DESIGN.md. The sidecar runs pi-durable's own storage core over tables the Rails migration creates, and Rails reads those same tables. There is one copy of the agent state. Both test suites pass on both databases.

What the app author does

Install

bundle add durable_agent
bin/rails g durable_agent:install   # migration, initializer, mount, Procfile.dev line
bin/rails db:migrate                # twelve durable_agent_* tables
bin/dev                             # web, sidecar

Use

conversation = DurableAgent.start            # model from config
conversation.say("Summarize the invoice",
                 request_id: message.id)      # idempotent
conversation.transcript                      # pi-durable's own entries
conversation.busy?                           # the pi.live document

# in the view
turbo_stream_from conversation               # refresh broadcasts, morph

That is the public surface. Tools are declared in Ruby (below). say is idempotent on request_id and returns the submission row, which the sidecar commits before it answers. The app brings its own pg or sqlite3 gem; durable_agent depends on neither.

Why one database

pi-durable's storage is pluggable: its portable SQLite core needs only a small database facade underneath it, and it ships a conformance suite for anyone who supplies one. The sidecar supplies two, pi-durable's own for SQLite and the gem's for Postgres, and runs the unchanged core over tables the Rails migration creates. That is the whole trick. Agent state is written once, by the process that produces it, into the database the app already operates, backs up and replicates.

One copy of the state, so nothing has to agree with anything. There is no second store to keep in step, no copy that can fall behind, no process whose only job is to notice changes. Rails reads pi-durable's tables with ordinary read-only models; the sidecar tells Puma that a conversation changed over HTTP, and Puma broadcasts. Crash safety is pi-durable's own, in the database it already commits to.

Runtime shape

One sidecar per app. SQLite suits development, test and single-host production, where both processes open the same file; Postgres suits everything else, including web and sidecar on different hosts.

What a message does

The storage layer

pi-durable ships a portable storage core, SqliteStorage, that speaks to a small database facade (exec, run, get, all, transaction, close, ? placeholders, SQLite dialect). The sidecar gives it one of two adapters behind that facade, chosen by the scheme of DATABASE_URL, and wraps the resulting Storage twice.

The storage core speaks SQLite; sidecar/src/db/translate.ts (69 lines) rewrites four things and memoizes by SQL text. The gem's own SQL (settings, credentials, reports) is written once in the SQLite dialect and goes through the same translation.

Rails owns the schema

The install migration creates all twelve tables with adapter-neutral Rails DDL; the same file is copied into test/dummy/db/migrate. Nine are pi-durable 1.3.0's SQLite schema (version 1) under the durable_agent_ prefix, with the same table, column and index names, partial index included, so the storage core runs over them unchanged. Deliberate differences from pi-durable's own DDL:

  • text, never jsonb. record and content hold JSON text. jsonb rejects \u0000, which would turn one model output into a fatal commit.
  • bigint ids and seqs, with no sequence or default on harness ids: pi-durable mints them.
  • No STRICT, no CHECK constraints (pi-durable validates its own writes), no foreign keys (it writes the rows of one commit in its own order), no seed rows.

What the sidecar does at boot

  1. Records the gem's schema version.INSERT … ON CONFLICT DO NOTHING into durable_agent_settings. A "no such table" or 42P01 here stops the boot with "run bin/rails db:migrate".
  2. Checks the harness tables exist.One SELECT id FROM durable_agent_conversations LIMIT 0, else MissingSchema.
  3. Seeds the two singleton rows.durable_schema (1, CURRENT_SQLITE_SCHEMA_VERSION) and durable_metadata (1, next_id '2', next_seq 1), both ON CONFLICT DO NOTHING, so a database loaded from schema.rb works.
  4. Refuses an older harness schema.A pi-durable release with a newer schema is a gem upgrade that ships a Rails migration. The sidecar never migrates.
  5. Opens SqliteStorage under the prefix.It finds the version current and runs no migrations. The gem's own schema_version row is checked too: newer than the gem refuses to boot, older warns.
  6. Serves, loads tools, then resumes.The HTTP server starts, the Ruby tool definitions are fetched with retries for up to 60 s, and only then does the Harness resume interrupted runs, so a replay-safe tool call interrupted by a restart runs again instead of settling as interrupted. Until then submissions and aborts answer 503 starting and /health says resumed: false.
  7. Supervises the Harness.pi-durable treats a storage error as fatal to its session; the sidecar watches harness.closed and exits 1 on a failed session so a supervisor restarts it. An uncaught exception does the same. A missing table at any boot step is reported as "run bin/rails db:migrate".

Two commit wrappers

Documents are stored as bases

pi-durable stores a document as a base revision plus chord deltas, and checkpoints a new base only when the document's definition says so (pi.live when idle, pi.inbox when empty). Without help, Rails would have to replay chord deltas to read a streaming pi.live.

withBaseDocuments (in documents.ts) intercepts commit: for each delta on a current-only document (conversation scope with history: "latest", or any task or session scope, the same rule the storage core uses to keep one revision), it reads the current value, applies the ops with chord's apply on a structured clone, and commits a base of the same version instead. The storage core then drops the earlier revisions, so such a document always has exactly one revision row. Commits through the wrapper are serialized so the read and the commit cannot interleave. Deltas on rewindable documents pass through.

Change tracker and events

ChangeTracker (in events.ts) also wraps commit. Before the commit it names the conversations the batch will touch: conversation, entry and submission writes directly; document writes through a read-through cache from document id to conversation, sharing the base rewrite's read. A failed lookup skips that document and is logged; nothing after the commit can reject it, so the event path never decides a commit's fate. Task writes are ignored.

Events batches them with new report ids and posts {"conversations": [7, 9], "reports": [3], "auth": ["openai"]} (the auth key when a sign-in completed or a provider signed out) to /durable_agent/events: at most every 100 ms while changes keep coming, one retry after 1 s, then a warning and drop. Best effort, by design. Unset DURABLE_AGENT_RAILS_URL disables events; shutdown flushes them.

The contract

Two halves, two version numbers, both reported by /health: the gem's schema (2, in durable_agent_settings) and pi-durable's (1 for 1.3.0, in durable_agent_durable_schema). The sidecar ships inside the gem, so the pair is always compatible; DESIGN.md is the normative version. Everything except /health needs Authorization: Bearer, compared in constant time on both sides.

HTTP API (gem → sidecar)

GET /health{ok: true, schemaVersion: 2, harnessSchemaVersion: 1, database: "postgres" | "sqlite", model: {provider, modelId}}
POST /conversations{model?, instructions?} → 201 {id}; 422 {error, suggestions} for an unknown model
POST /conversations/:id/submissions{content, request_id, when_busy?} → 202 {id, status}; 409 conversation_busy; 404. Idempotent on request_id; the row is committed before the 202.
POST /conversations/:id/abort200 {ok: true}
GET /auth{provider → {type: "oauth" | "api_key"} | null}
POST /auth/:provider/loginsstart; GET …/:id polls, POST …/:id/callback finishes, DELETE …/:id cancels
DELETE /auth/:providersign out
POST /tools/reloadre-fetch tool definitions from Rails → {tools: [names]}

Events endpoint (sidecar → gem)

POST /durable_agent/events, body {"conversations": [ids], "reports": [ids]}. For each conversation that exists, Puma calls config.on_change.call(conversation); for each report, config.on_report.call(report). Unknown ids are skipped; callback errors go to Rails.error.report and never fail the request. Responds 204.

Tools protocol (sidecar → gem)

GET /durable_agent/tools returns [{name, description, parameters, replay}]. At boot a failed fetch retries in the background (500 ms doubling to 10 s, for up to 60 s) while the sidecar serves requests, because bin/dev starts node before Puma listens. POST /durable_agent/tools/:name takes {arguments, conversation_id, call_id}; 200 {result}, else {error} becomes an error result. 120 s timeout.

Tools in Ruby

The sidecar is generic: it fetches definitions and installs them as one extension that POST /tools/reload replaces in place.

# app/tools/lookup_invoice.rb
class LookupInvoice < DurableAgent::Tool
  description "Fetch one invoice by number"
  param :number, :string, "Invoice number like INV-1042"
  replay :safe                      # no side effects; may rerun after a crash

  def call(number:)
    Invoice.find_by!(number:).as_json(only: %i[ number total status due_on ])
  end
end

# config/initializers/durable_agent.rb
DurableAgent.configure do |config|
  config.model = "openai/gpt-6.1-sol"
  config.tools = %w[ LookupInvoice ]   # class names survive code reloading; classes work too
end

Every model is readonly? and sits directly on a pi-durable table through the HarnessRecord concern: a write from Rails would bypass the harness. Ids are pi's own. Records keep pi-durable's shapes as JSON text (attribute :record, :json); Entry#kind, data and model read from the record because there are no such columns, so kind filtering on entries (visible, of_kind) happens in Ruby and returns arrays.

The document rule

A document's current value is the content of its newest base revision. The base-document wrapper guarantees no delta follows it for any document Rails reads. If the newest revision is a delta (a rewindable document that does not checkpoint), DurableAgent::Document#value raises DurableAgent::Document::HistoryNotSupported rather than guess; none of the pi.* documents Rails reads do.

JSON-encoded columns

pi-durable indexes a few values as JSON-encoded strings: tasks.kind and documents.kind hold "\"pi.live\"", submissions.request_id holds "\"42\"", documents.key_value the encoded key. The models decode them on read, and scopes such as for_request and of_kind encode their argument with to_json.

config.on_change = ->(conversation) { … } and config.on_report = ->(report) { … } both default to Turbo::StreamsChannel.broadcast_refresh_to. The event names the conversation; the tables hold what changed, so the callback needs nothing else.

Deliberately out of scope

  • Per-user credentials. One set of provider sign-ins per app.
  • More than one sidecar. One process per app and database.
  • Compaction, reset, task graph, usage, SSE. pi-durable has them; the routes wait for a need.
  • Forked conversations' inherited entries. entries are a conversation's own rows.
  • A Ruby port of chord deltas. The base-document wrapper makes it unnecessary for every document Rails reads.
  • Any UI, and MCP. The engine serves only the endpoints the sidecar calls; tools are Ruby classes.

Design decisions

  • The sidecar never runs DDL. Rails migrations own every schema change, including future pi-durable schema versions, which ship as gem migrations. pi-durable's storage would otherwise migrate on open, so the sidecar checks the version first.
  • Boot fails early and clearly. Every boot step runs inside one handler, so a missing table anywhere is MissingSchema. Settings row first (so a missing table fails with "run bin/rails db:migrate"), then the conversations table, then the seed, then the version check, then SqliteStorage.open. Seeding before the check is what lets a database loaded from schema.rb, which carries no rows, boot.
  • The Harness closes the database handle. SqliteStorage.close closes its facade, so harness.close closes the database; both adapters' close are idempotent, and shutdown closes the Harness, flushes events, then closes the database again harmlessly.
  • Postgres runs in UTC. CURRENT_TIMESTAMP lands in timestamp without time zone columns that Rails reads as UTC, so every pooled connection starts with -c TimeZone=UTC, appended to any options the URL carries.
  • Postgres still needs CREATE on the schema. The one DDL statement pi-durable still sends is its CREATE TABLE IF NOT EXISTS durable_agent_durable_schema, a no-op over the existing table, but Postgres checks the permission first.
  • Rails index syntax reproduces pi-durable's indexes. order: { id: :desc } and where: "head IS NOT NULL" give the same id DESC columns and partial index, under pi-durable's own index names.
  • Rails' default primary keys, on purpose. The harness tables use Rails' own id: INTEGER PRIMARY KEY on SQLite, a rowid alias like pi-durable's DDL, and bigserial on Postgres whose sequence is never used because the sidecar supplies every id. Conversations, entries and submissions also carry a created_at the database fills, since pi-durable records no times.
  • One serial queue on Postgres, as on SQLite. A pool of two, with nothing else running while a transaction is open, matches pi-durable's node adapter. A checked-out client carries an error listener for its whole life, so a dropped connection inside a transaction rejects that transaction instead of crashing the process. Outside a transaction only a plain SELECT is retried after a connection error; a write whose response was lost is never sent twice.
  • SQLite waits without stalling. node:sqlite's busy wait is synchronous, so the adapter keeps it at 100 ms and retries a busy BEGIN IMMEDIATE asynchronously, 25 ms doubling to 500 ms, for up to 30 s. The rule for a shared file: no other writer holds the write lock longer than 30 s.
  • Shutdown has a deadline. Open requests get 10 s, reports in flight are awaited, the Harness closes, events flush; the whole thing has 30 s, and a second signal exits at once.
  • Events are a hint, not a log. Debounced, retried once, then dropped. Correctness lives in the tables; an event only shortens the time until a page shows it.
  • Documents are folded exactly where the core keeps one revision. The base rewrite applies to every current-only document; rewindable conversation documents keep their deltas, and HistoryNotSupported makes a violation loud.
  • Small guarantees. Zero-setup tokens in development and test, derived from secret_key_base; tools may be given as class names so they survive reloading; a wrong default model does not take the service down; tools reload in place.

Known limitations

  • A report raised while the Harness is closing is lost. Closing the Harness closes the database; reports in flight before that are awaited, one raised during the close itself cannot be stored.
  • Refresh broadcasts arrive up to every 100 ms per streaming conversation. The event debounce bounds the rate; the page refresh is not debounced further.
  • pi-durable 1.3.0 reports carry no conversation. They land on the durable_agent:reports stream rather than a conversation's.
  • A revoked OAuth credential reads as connected until a run fails. The auth status only checks that a credential is stored; a refresh token revoked elsewhere (OpenAI rotates them, so one grant cannot serve two installations) surfaces as a model_error on the next message, which the transcript shows.
  • Smaller ones. Demodulized tool names can collide; very long request ids or document keys could exceed Postgres index entry limits; sslmode=prefer and allow pass through to node unchanged, where they mean full verification; a role on Postgres 15+ needs CREATE on the schema for pi-durable's one CREATE TABLE IF NOT EXISTS; the 30 s shutdown deadline and the uncaught-exception exit are not covered by tests.
