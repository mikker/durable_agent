durable_agent

pi-durable as a Rails gem. One bundle add, one migration, one extra process, one database: the app's own Postgres or SQLite.

A Rails engine plus a bundled Node sidecar. The sidecar runs pi-durable's storage core over tables a Rails migration creates. Rails reads the same tables. One copy of the state. Contract: DESIGN.md.

Install, use

Install

bundle add durable_agent
bin/rails g durable_agent:install   # migration, initializer, mount, Procfile.dev line
bin/rails db:migrate                # twelve durable_agent_* tables
bin/dev                             # web, sidecar

Use

conversation = DurableAgent.start         # model from config
conversation.say("Summarize the invoice",
                 request_id: message.id)  # idempotent on request_id
conversation.transcript                   # pi-durable's own entries
conversation.busy?                        # the pi.live document

# in the view
turbo_stream_from conversation            # refresh broadcasts, morph

say is idempotent on request_id and returns the submission row, committed before the sidecar answers. Tools are Ruby classes (below). The app brings its own pg or sqlite3.

Why one database

pi-durable's storage core is portable: SQLite dialect over a small facade, with a conformance suite. The sidecar supplies the facade for SQLite and for Postgres and runs the unchanged core over the Rails tables.

One copy of the state. No mirror, no sync, no relay. Rails reads the tables. The sidecar tells Puma what changed. Puma broadcasts. Crash safety is pi-durable's own.

Runtime shape

One sidecar per app. SQLite for development, test and one host. Postgres for the rest.

What a message does

The storage layer

SqliteStorage talks to a facade: exec, run, get, all, transaction, close, ? placeholders. The scheme of DATABASE_URL picks the adapter. Two wrappers sit on the resulting Storage.

Boot

  1. Record the gem's schema version.Missing table: stop with "run bin/rails db:migrate".
  2. Check the harness tables.SELECT id FROM durable_agent_conversations LIMIT 0, else MissingSchema.
  3. Seed the two singleton rows.ON CONFLICT DO NOTHING, so a schema.rb load boots.
  4. Refuse a schema mismatch.Newer pi-durable schemas ship as gem migrations. The sidecar never migrates.
  5. Open SqliteStorage under the prefix.Gem schema_version newer than the gem refuses; older warns.
  6. Serve, load tools, then resume.Tools are fetched with retries for 60 s before the Harness resumes, so an interrupted replay-safe tool call reruns. Until then: 503 starting, resumed: false.
  7. Supervise.A failed session or an uncaught exception exits 1. The supervisor restarts.

Two commit wrappers

Documents stored as bases

pi-durable stores a document as a base plus chord deltas and checkpoints a new base only when the definition says so. Rails would have to replay deltas to read a streaming pi.live.

withBaseDocuments intercepts commit. For each delta on a current-only document it reads the value, applies the ops, and commits a base of the same version. The core then keeps one revision row. Rewindable documents pass through. Commits are serialized.

Change tracker, events

ChangeTracker names the conversations a batch touches before the commit. Nothing after the commit can reject it.

Events posts {"conversations": [7], "reports": [3], "auth": ["openai"]} to /durable_agent/events: at most every 100 ms, one retry after 1 s, then drop. Unset DURABLE_AGENT_RAILS_URL disables it. Shutdown flushes.

The contract

Two version numbers in /health: the gem's schema (2) and pi-durable's (1). The sidecar ships inside the gem, so they always match. Everything but /health needs Authorization: Bearer, constant-time on both sides.

HTTP API (gem → sidecar)

GET /health{ok, schemaVersion, harnessSchemaVersion, database, model, tools, resumed}
POST /conversations{model?, instructions?, account?} → 201 {id}; 422 unknown model or invalid account. With account, the conversation runs on that account's credential.
POST /conversations/:id/submissions{content, request_id, when_busy?} → 202 {id, status}; 409 busy; 404. Idempotent; row committed first.
POST /conversations/:id/abort200 {ok}
GET /auth?account={provider → {type, source} | null}, the app's or the account's
PUT /auth/:provider/api_key?account={key} → stored encrypted; 422 blank key
POST /auth/:provider/logins?account=start; GET …/:id polls, POST …/:id/callback finishes, DELETE …/:id cancels
DELETE /auth/:provider?account=sign out
POST /tools/reloadre-fetch tools → {tools}

Events (sidecar → gem)

POST /durable_agent/events. Per conversation: config.on_change. Per report: config.on_report. Per credential change: config.on_auth with provider ids, scoped for accounts (openai@u42). Unknown ids skipped, callback errors reported, always 204.

Tools (sidecar → gem)

GET /durable_agent/tools → [{name, description, parameters, replay}], retried at boot for 60 s. POST /durable_agent/tools/:name with {arguments, conversation_id, call_id} → {result} or {error}. 120 s timeout.

Accounts

An account names whose credential a conversation runs on. It is an app-chosen string, typically a user id. The sidecar carries it in the provider id: openai@u42 is account u42's OpenAI, openai@u42/gpt-6.1-sol its model ref, and no @ is the app's own. pi-ai keys credentials, logins and auth checks by provider id, and each conversation pins its provider in pi.agent, so one mechanism covers who pays:

Who paysCredentialConversation
the app, for everyoneOPENAI_API_KEY, connection.set_api_key, or Sign in with ChatGPT in SettingsDurableAgent.start
each user, API keyConnection.new("openai", account: user.id).set_api_key(key)DurableAgent.start(account: user.id)
each user, ChatGPT planConnection.new("openai", account: user.id).start_loginDurableAgent.start(account: user.id)

The sidecar registers a clone of the base provider under the scoped id on demand and at boot from the credentials table: same catalog, same auth methods, one more credential row. A conversation on an account whose credential is gone settles no_model. Usage per account is the sum of pi.usage over its conversations.

Sign in with ChatGPT is pi-ai's OpenAI OAuth: a public client registered per login, scope chatgpt.tokens.use.direct, the token sent to the Responses API, usage drawn from the signed-in user's plan. The redirect is 127.0.0.1:1455: on the sidecar's host the listener completes the login; elsewhere the user pastes the final URL into the app.

Tools in Ruby

The sidecar fetches definitions and installs them as one extension. POST /tools/reload replaces it in place.

# app/tools/lookup_invoice.rb
class LookupInvoice < DurableAgent::Tool
  description "Fetch one invoice by number"
  param :number, :string, "Invoice number like INV-1042"
  replay :safe                        # no side effects; may rerun after a crash

  def call(number:)
    Invoice.find_by!(number:).as_json(only: %i[ number total status due_on ])
  end
end

# config/initializers/durable_agent.rb
DurableAgent.configure do |config|
  config.model = "openai/gpt-6.1-sol"
  config.tools = %w[ LookupInvoice ]  # class names survive code reloading
end

Every model is readonly?. Ids are pi's. Records stay JSON text (attribute :record, :json). kind, data, model live in the record, so kind filters run in Ruby and return arrays.

The document rule

A document's value is its newest base revision. The base wrapper guarantees no delta follows it for anything Rails reads. If one does, Document#value raises HistoryNotSupported.

JSON-encoded columns

tasks.kind, documents.kind, documents.key_value and submissions.request_id hold JSON strings ("\"pi.live\""). Models decode on read; for_request and of_kind encode.

on_change, on_report and on_auth default to Turbo::StreamsChannel.broadcast_refresh_to. The event names the conversation; the tables hold the rest.

Out of scope

  • More than one sidecar. One process per app and database serves every user.
  • Compaction, reset, task graph, SSE routes. pi-durable has them; no need yet.
  • Forked conversations' inherited entries. entries are a conversation's own rows.
  • A Ruby port of chord deltas. The base wrapper makes it unnecessary.
  • UI, MCP. Tools are Ruby classes.

Decisions

  • The sidecar never runs DDL. Migrations own every schema change, pi-durable's included.
  • Boot fails early. Every step runs in one handler; any missing table is "run bin/rails db:migrate". Seeding before the version check lets a schema.rb load boot.
  • The Harness closes the database. close is idempotent on both adapters.
  • Postgres runs in UTC. -c TimeZone=UTC on every connection.
  • Postgres needs CREATE on the schema. pi-durable's one CREATE TABLE IF NOT EXISTS, a no-op, still checks it.
  • Rails index syntax reproduces pi-durable's indexes. order: { id: :desc }, where: "head IS NOT NULL", pi-durable's names.
  • Rails' default primary keys. Rowid alias on SQLite, bigserial on Postgres, sequence unused. Conversations, entries, submissions get a created_at.
  • One serial queue on Postgres, as on SQLite. Pool of two. The checked-out client has an error listener, so a dropped connection rejects the transaction, not the process. Only plain SELECTs retry.
  • SQLite waits without stalling. 100 ms synchronous busy wait, then async retries of BEGIN IMMEDIATE up to 30 s.
  • Shutdown has a deadline. 10 s for requests, 30 s total, second signal exits.
  • Events are hints. Debounced, one retry, then dropped. The tables are correct without them.
  • Bases exactly where the core keeps one revision. Rewindable documents keep deltas; HistoryNotSupported makes a violation loud.
  • Accounts are provider ids. openai@u42 rides every path pi-ai and pi-durable already key by provider: credential rows, logins, the model pinned per conversation. No schema change, no pi-durable change.
  • Small guarantees. Zero-setup tokens in development and test. Tools as class names survive reloading. A wrong default model does not take the service down.

Known limitations

  • A report raised while the Harness closes is lost.
  • Refresh broadcasts up to every 100 ms per streaming conversation.
  • pi-durable 1.3.0 reports carry no conversation. They land on durable_agent:reports.
  • A revoked OAuth credential reads as connected until a run fails. OpenAI rotates refresh tokens; one grant cannot serve two installations. The next message shows a model_error.
  • Smaller. Demodulized tool names can collide; very long request ids or keys can exceed Postgres index limits; sslmode=prefer and allow mean full verification in node; the shutdown deadline and the uncaught-exception exit are untested.
