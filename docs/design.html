durable_agent: pi-durable as one Rails gem

One bundle add, one migration, one extra process. The gem carries the sidecar inside it; the app never sees two products.

durable_agent is a placeholder name. Everything below is sized from a working reference integration (a Rails chat app with a hand-rolled sidecar): what to keep, what to cut, and what the contract between the two halves has to be so the pi-durable churn stays inside the gem.

What the app author does

Install

bundle add durable_agent
bin/rails g durable_agent:install   # migration, initializer, Procfile.dev lines
bin/rails db:migrate
bin/dev                             # web, css, sidecar, relay

Use

conversation = DurableAgent.start            # model from config
conversation.say("Summarize the invoice",
                 request_id: message.id)      # idempotent
conversation.transcript                      # mirrored entries
conversation.busy?                           # pi.live document

# in the view
turbo_stream_from conversation               # refresh broadcasts

That is the whole public surface for v0. Tools are the one addition that makes it feel native, and they are declared in Ruby (below).

The contract

Two halves, one version number. The sidecar ships inside the gem, so the pair is always compatible, but the contract still has to be explicit: it is what lets the gem upgrade pi-durable without touching the app.

HTTP (sidecar ← gem)

GET /healthliveness, schema version
POST /conversations{model?, instructions?} → {id}
POST /conversations/:id/submissions{content, request_id, when_busy?} → {id}, 409 busy, 422 unknown model
POST /conversations/:id/abortstop the run
GET /auth{provider → type | null}
POST /auth/:provider/loginsstart; /:id/callback finishes
DELETE /auth/:providersign out

Postgres (sidecar → gem)

agent_conversationspi ids, parent, owner
agent_entriesimmutable; kind, model, data
agent_documentspi.live, pi.inbox, pi.agent, pi.usage
agent_submissionsrequest_id, status, reason
agent_reportsfaulted and parked tasks
agent_credentialssidecar only; Rails has no model
NOTIFY agent_mirror{conversationId, entries[], docs[]}
NOTIFY agent_reports{id, conversationId, type}

HTTP (gem ← sidecar)

One route the other way: POST /durable_agent/tools/:name with the same bearer token. It is the only reason the sidecar needs to know the Rails URL.

Tools in Ruby

This is the one feature beyond the reference integration that v0 should include. Without it every tool is TypeScript inside the gem, which defeats the point of a Rails gem. With it the sidecar stays generic.

# app/tools/lookup_invoice.rb
class LookupInvoice < DurableAgent::Tool
  description "Fetch one invoice by number"
  param :number, :string, "Invoice number like INV-1042"
  replay :safe                      # no side effects; may rerun after a crash

  def call(number:)
    Invoice.find_by!(number:).as_json(only: %i[ number total status due_on ])
  end
end

# config/initializers/durable_agent.rb
DurableAgent.configure do |config|
  config.model = "openai/gpt-6.1-sol"
  config.tools = [ LookupInvoice ]
end

Distribution. v0 ships sidecar/dist/sidecar.js, one esbuild bundle inside the gem, and requires Node 22 or newer on the host. That is the same ask as jsbundling. The step after that is a compiled binary per platform, published as platform gems the way tailwindcss-ruby does it, so Node disappears from the requirements. The runtime check lives in one place, DurableAgent::Sidecar.command, so the swap touches nothing else.

Deliberately out of v0

  • Per-user credentials. Sign in with ChatGPT is per installation. Multi-user apps will want per-account routing; that changes the sidecar's model resolution and is a v1 topic.
  • More than one sidecar. One process per database. Tenant namespaces via the pi table prefix come later, with docs on who owns which storage.
  • Compaction, reset, task graph, usage. pi-durable has them; the routes are ten lines each when someone needs them.
  • Any UI. The gem renders nothing. A chat scaffold generator can come in a later release.
  • MCP. pi-ai supports it; exposing it means the sidecar runs other processes, which deserves its own design.

Build order

  1. Extract the sidecar into sidecar/ inside a new gem repo and cut it to 7 routes.Add GET /health schema version, the 422 for unknown models, and the generic Rails tool. Keep the mirror and credential tests.
  2. Move the Ruby into an isolated engine.Models, client, relay with the refresh-broadcast default, DurableAgent::Tool, tools controller. Port the reference tests; the round-trip test becomes the gem's main integration test.
  3. Write the installer and the two rake tasks.Migration with agent_schema_version, initializer, Procfile lines, token in credentials. Env derivation from Rails config.
  4. Bundle the sidecar with esbuild and vendor dist/sidecar.js in the gem.One CI job builds it; the gemspec includes it. Document the Node requirement.
  5. Run a real app on the gem.Delete the duplicated code from the reference app, keep its chat UI as app code. If it runs on the gem with no local patches, v0 is done.

Order matters only in one place: the contract version goes in before anything is published, because the first app on the gem must survive the first pi-durable upgrade without a migration.
