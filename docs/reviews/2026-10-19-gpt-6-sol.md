## Findings, ranked by severity

1. **High — Settled submissions can disappear from the mirror after a crash.** [mirror.ts](/Users/mikker/dev/durable_agent/sidecar/src/mirror.ts:63) re-arms only submissions returned by the startup inspection, while [track](/Users/mikker/dev/durable_agent/sidecar/src/mirror.ts:115) and the settlement write are asynchronous. If the harness commits a submission and it settles before the sidecar writes its Postgres row, a crash leaves the submission in SQLite but absent from Postgres. Startup does not reconcile settled submissions, so Rails may never see that input or its outcome. This breaks the README’s crash-recovery claim.

2. **High — Concurrent frame writes can move mirrored documents backward.** [mirror.ts](/Users/mikker/dev/durable_agent/sidecar/src/mirror.ts:175) calculates changes from shared bookkeeping, and [watch.start](/Users/mikker/dev/durable_agent/sidecar/src/mirror.ts:107) passes an async writer without serializing frames. If frame B commits before the slower frame A, A can overwrite `pi.live` or another document with older JSON; its completion also replaces the remembered hash. Rails can then show stale run state until another frame happens.

3. **High — A failed frame has no guaranteed retry.** [mirror.ts](/Users/mikker/dev/durable_agent/sidecar/src/mirror.ts:215) clears bookkeeping after a Postgres failure but retries only when a *next* frame arrives. If the failed write was the final assistant frame, the transcript and documents stay incomplete for the rest of that sidecar process’s lifetime. Boot reconciliation may repair them, but the sidecar need not restart.

4. **High — OAuth credentials are stored as readable JSON in the application’s primary database.** The [migration](/Users/mikker/dev/durable_agent/lib/generators/durable_agent/install/templates/create_durable_agent_tables.rb.tt:61) creates a plain `jsonb` credential column, and [credentials.ts](/Users/mikker/dev/durable_agent/sidecar/src/credentials.ts:60) writes tokens into it directly. “Rails has no model” does not restrict SQL access: database readers, backups, and dumps can expose refresh tokens. This is an explicit design choice in `DESIGN.md`, but it has a substantial security consequence for a gem installed in other applications.

5. **Medium — A lost LISTEN connection stops live delivery until the relay is restarted.** [relay.rb](/Users/mikker/dev/durable_agent/lib/durable_agent/relay.rb:15) opens one raw connection and loops without reconnecting. A Postgres failover or network interruption exits the relay; notifications emitted while it is down are transient. The mirror remains readable, but subscribed pages and callback consumers can miss updates indefinitely.

6. **Medium — Packaging depends on the build path used.** The [gemspec](/Users/mikker/dev/durable_agent/durable_agent.gemspec:21) includes `sidecar/dist` but excludes `sidecar/src`; `dist` is ignored and untracked at HEAD. The [Rake build task](/Users/mikker/dev/durable_agent/Rakefile:8) creates the bundle, but a direct `gem build durable_agent.gemspec` would package neither executable source nor bundle. [Sidecar.command](/Users/mikker/dev/durable_agent/lib/durable_agent/sidecar.rb:29) would then select a missing source path, making the installed gem unable to start.

7. **Medium — Schema-version mismatch is silently accepted.** [recordSchemaVersion](/Users/mikker/dev/durable_agent/sidecar/src/credentials.ts:98) uses `ON CONFLICT DO NOTHING`; [main.ts](/Users/mikker/dev/durable_agent/sidecar/src/main.ts:25) proceeds without checking the stored value. A database marked with a newer or incompatible mirror schema can boot this sidecar and fail later during writes. The credential test explicitly confirms that version `"7"` remains accepted.

These are code-review findings; I made no edits or test runs. The frame-order finding depends on the watch callback allowing overlapping async calls, which this repository does not constrain.

## Three changes I would make first

1. Reconcile **all** submissions from harness storage on boot, including settled ones.
2. Serialize mirror writes per conversation and retry failed final frames independently of future activity.
3. Encrypt stored credentials with a key outside Postgres, and document the database access boundary.
