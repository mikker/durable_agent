# Independent review by GPT-6 Sol through Codex (2026-10-19, HEAD e0d356e, one-database design)

Read-only. Codex's sandbox could not open SQLite files or reach Postgres, so neither suite ran; `tsc --noEmit` passed.

## 1. Confirmed findings

- **High — A report can be lost during an orderly shutdown.** `sidecar/src/reports.ts:29` starts the database insert without returning or tracking its promise. `sidecar/src/main.ts:82` then closes the harness and flushes events, but `events.flush()` cannot wait for a report insert that has not yet called `events.report(id)`. A report raised just before `SIGTERM` can therefore miss both persistence and delivery. Verified by the promise and shutdown code paths; not reproduced against a database.
- **Medium — The document wrapper does not establish its stated rule for every latest-history document.** `sidecar/src/documents.ts:86` rewrites deltas only when the document has conversation scope. A latest-history document with session or task scope retains a delta, while `DurableAgent::Document#value` cannot read a value ending in one. Verified by the explicit scope guard. The tests cover conversation-scoped latest and rewindable documents, not this case.
- **Medium — Post-commit owner lookup can turn a successful commit into an error.** `sidecar/src/events.ts:133` awaits the storage commit and then performs document owner reads before announcing changes. If one of those reads fails, `commit` rejects even though the writes are durable, and no event is queued. A caller may interpret the operation as failed and retry it. Verified by the order of operations in `ChangeTracker.commit`; not fault-injected.
- **Low — An unknown model at boot is handled less safely than the contract says.** `sidecar/src/harness.ts:65` logs and continues after model validation fails, but `sidecar/src/main.ts:52` subsequently creates or opens the root with that model outside the boot error handler. Whether this stops startup depends on pi-durable's `root` behaviour; not confirmed.

## 2. Plausible findings not reproduced

- `sidecar/src/documents.ts:98` reads each delta's starting value from storage before committing the batch. Two changes to the same document in one batch, or a create followed by a change in that batch, may bypass or miscompute the base rewrite. Needs a focused batch probe.
- `sidecar/src/db/postgres.ts:160` retries a connection-class failure on an individual statement. A lost response after a server-side commit would make retrying a non-idempotent statement unsafe; not reproduced.
- `sidecar/src/main.ts:40` does not route a missing-table error from `installationDeviceId` through its `MissingSchema` handler, despite the contract's "anywhere in that sequence" wording.

## 3. Contract disagreements

- DESIGN.md says deltas on latest-history documents are folded into bases. The implementation limits that to conversation scope.
- DESIGN.md says a missing table anywhere during boot is reported as `MissingSchema`. The device-id step is outside that handling.
- DESIGN.md says shutdown flushes events after closing the harness. It does, but the untracked report writes are not part of that flush.

## 4. Test quality

Neither Rails suite nor the sidecar suites reached their tests in the sandbox (`EPERM` on temp files and on localhost Postgres). The suites have useful conformance, translation, model, event and faux-harness coverage; the Postgres translator test runs pi-durable's own migrations, stronger than string assertions. The document tests establish a single streamed `pi.live` path, not all document scopes or multiple changes within one commit. The event tests establish ordinary batching and retry, not failure after a successful commit or a report racing shutdown.

## 5. Three changes first

1. Track report insert promises and await them before closing the database and flushing events.
2. Make the base rewrite correct for every latest-history document and for multiple writes to one document in a batch, with tests.
3. Ensure notification lookup failures cannot change the outcome of an already successful storage commit.

## 6. Prerelease readiness

Not ready to sign off: the shutdown report-loss path and the document-handling mismatch warrant fixes, and this environment could not validate database behaviour.
